# GUNG:ON Vault 운영 규칙 (RULE)

이 문서는 `MJC/GUNG ON/` vault를 어떻게 정리하고 유지할지에 대한 규칙이다. 여러 번 파일 구조/이름이 바뀌면서 혼란이 있었기 때문에, 앞으로는 이 규칙을 기준으로 일관되게 관리한다. 사람이 읽어도, Claude가 읽어도 같은 규칙을 따르도록 쓴다.

---

## 1. 목적

- GUNG:ON 프로젝트의 기획/IA/브랜딩 문서를 한 곳에서, 최신 상태로, 헷갈리지 않게 관리한다.
- Figma·GitHub 등 외부 산출물과의 연결 관계를 놓치지 않는다.
- 문서가 여러 버전으로 갈라지거나, 어떤 게 최신인지 헷갈리는 상황을 방지한다.

---

## 2. 폴더 구조

```text
GUNG ON/
├─ 01_system/       인덱스 · 로그 · 운영 규칙 (이 폴더)
├─ 02_Service_Design/   서비스 기획
├─ 03_IA/               정보구조도
├─ 04_Branding/         브랜드 전략 · 네이밍 · 무드 · 컬러
├─ 05_Presentation/     발표자료 관련
└─ 05_research/         리서치 자료
```

- 폴더명 형식: `{2자리 번호}_{영문명}` (한글 폴더명은 점진적으로 영문으로 정리 중)
- 번호는 원칙적으로 겹치지 않게 매긴다. 겹치는 경우가 생기면(현재 05_Presentation/05_research) `01_system/index.md`의 "미해결 사항"에 기록하고 사용자 확인을 받는다.
- 새 도메인이 생기면 다음 번호로 폴더를 추가하고, 반드시 `index.md`에 등록한다.

---

## 3. 기본 작성 원칙

- **도메인마다 요약 Master 문서를 1개 유지한다.** (예: 서비스 기획 → `GUNGON_Service_Planning_VER 1.0.md`)
- 세부 내용이 많아 Master 하나로 감당이 안 되는 도메인(예: Branding)은 **STEP/주제별 상세 파일을 따로 둘 수 있다.** Master는 전체 요약, 상세 파일은 각 주제의 전문(全文) 역할을 한다.
- **기존 문서를 고쳐쓰지 않는다 — 버전을 올린다.** 큰 개정이 생기면 새 버전을 만들거나(`VER 1.0` → `VER 2.0`), 최소한 "최신 문서가 우선한다"는 원칙을 문서 안에 명시한다.
- **옛 버전을 삭제할지 보관할지는 사용자가 정한다.** 기본은: 먼저 `_archive_{날짜}/`로 옮겨두고, 사용자가 "삭제해줘"라고 명시하면 그때 완전히 삭제한다.
- 문서 안에 "Master Source Rule"처럼 우선순위 원칙을 명시해서, 문서끼리 충돌할 때 뭘 따라야 하는지 문서 자체에서 알 수 있게 한다.

---

## 4. 파일명 규칙

| 종류 | 형식 | 예 |
|---|---|---|
| 도메인 요약 Master | `GUNGON_{도메인}_VER {N}.0.md` | `GUNGON_Branding_VER 1.0.md` |
| STEP/주제별 상세 문서 | `{2자리번호}_GUNGON_{주제}_STEP{n}.md` | `03_GUNGON_Reference_DesignMethod_STEP3.md` |
| 문서 제목 | `# 문서 제목 (VER {N}.0)` | `# GUNG:ON BRAND STRATEGY (VER 1.0)` |
| 시스템 문서 | 대문자, 확장자만 (`index.md`, `log.md`, `RULE.md` 등 소문자/파스칼 혼용 가능) | `RULE.md` |

- 버전 번호는 정수.소수 형식(`1.0`, `1.1`, `2.0`)을 쓴다. 소폭 수정은 소수점을 올리고(1.0→1.1), 구조가 크게 바뀌면 정수를 올린다(1.x→2.0).
- 파일명에 공백을 쓸지 언더스코어를 쓸지는 혼재돼 있다(`GUNGON_Branding_VER 1.0.md`처럼 버전 표기 앞은 공백, 나머지는 언더스코어) — 새 파일도 이 패턴을 따른다.

---

## 5. 링크 · 참조 규칙

- 문서 안에서 다른 문서를 가리킬 때는 파일명을 그대로 적는다. (예: "기준 문서: `GUNGON_Service_Planning_VER 1.0.md`")
- Figma, GitHub 등 이 vault 밖의 리소스 링크는 전부 `01_system/index.md`의 "연결된 외부 리소스" 섹션에 모아둔다. 개별 문서 안에 흩어놓지 않는다.
- 다른 문서의 특정 섹션을 근거로 댈 때는 "파일명 + 섹션 번호/제목"까지 적는다. (예: "확정됨(`03_GUNGON_Reference_DesignMethod_STEP3.md` 섹션 13)")

## 6. index.md 갱신 규칙 (가장 중요)

**이 vault 안에서 파일을 추가·이동·이름변경·삭제할 때마다, 반드시 그 즉시 `01_system/index.md`의 파일 목록과 `01_system/log.md`를 함께 갱신한다.** 나중에 몰아서 하지 않는다.

- `index.md`는 항상 실제 파일 시스템과 100% 일치해야 한다. 일치하지 않으면 `index.md`가 틀린 것이다.
- 작업을 시작하기 전에는 먼저 실제 폴더 상태(`find`/`ls`)를 확인하고, `index.md`와 다른 점이 있으면(예: 사용자가 Obsidian에서 직접 리네임한 경우) 그 차이를 `index.md`와 `log.md`에 반영한 뒤 작업을 시작한다.
- `log.md`에는 "무엇을, 어디서, 어떻게" 바뀌었는지 최소 한 줄로 남긴다. 새 항목은 맨 위에 추가한다.

## 6-A. GitHub 미러 동기화 규칙

이 vault는 `https://github.com/shinhayoung02-cmd/gungon-figma-guide`(로컬: `C:\Users\Admin\Documents\gungon-figma-guide`)에 통째로 미러링된다.

**이 vault의 파일을 추가·이동·이름변경·삭제·수정할 때마다, 그 즉시 위 레포 폴더에도 같은 변경을 반영하고 커밋·푸시한다.** 요청을 따로 기다리지 않고 매번 한다(vault 안 문서를 고칠 때의 기본 동작). 레포 루트의 `README.md`는 `01_system/index.md`와 항상 같은 내용으로 유지한다.

## 7. 외부(Obsidian) 변경 감지

사용자가 Claude를 거치지 않고 Obsidian에서 직접 파일을 리네임/이동/삭제할 수 있다 — 실제로 여러 번 있었다(`GUNGON_Branding_Master.md` → `GUNGON_Branding_VER 1.0.md` 등). 이런 변경은 로그에 자동으로 남지 않는다. 그래서:

- 이 vault 관련 작업을 시작할 때는 `index.md`를 눈으로만 믿지 말고, 실제 파일 목록과 대조한다.
- 차이가 발견되면 조용히 넘어가지 말고 `index.md`/`log.md`를 갱신하고, 필요하면 사용자에게 짧게 알린다.
